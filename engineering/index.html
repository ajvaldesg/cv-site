Architecture

A browser requests the site from Azure's global edge. Static assets come from the CDN node closest to the visitor; anything under /api/* is routed to managed Azure Functions running in the same Static Web App. Those functions read and write Azure Table Storage and emit traces and metrics to Application Insights. Deployments are triggered by a push to main and built by GitHub Actions.

Decisions worth defending

Short ADRs — the reason each choice is right for this workload, and what it costs.

ADR-01 · Static Web Apps over App Service or AKS

One resource serves the frontend from the edge and hosts the API as managed functions.

Why: zero servers to patch, TLS and CDN included, and the cost at this scale is literally $0. A container platform here would be infrastructure for its own sake.

ADR-02 · Table Storage over Cosmos DB or SQL

A counter and a contact inbox are key-value workloads: one partition, one row per item.

Why: pennies per month, no RU provisioning, no cold-start penalty. Cosmos would be the right call if I needed multi-region writes or sub-10 ms p99 on a hot path — I don't.

ADR-03 · No SPA framework

Plain HTML, CSS and ~150 lines of JavaScript. No React, no bundler, no node_modules on the frontend.

Why: the page renders before the JS parses, works with JS disabled (minus the counter/form), and there is no dependency supply chain to audit. A CV does not need a virtual DOM.

ADR-04 · Degrade, never break

Every API call is wrapped: if storage is unreachable or the function is cold, the page still renders and the badge simply says so.

Why: the primary job of this site is to be readable. Telemetry niceties must never be able to take the content down.

ADR-05 · Cost discipline: no paid web tests

Availability is watched through an edge 5xx metric alert (≈$0.10/month), not a synthetic ping test.

Why: standard web tests bill $0.00056 per execution — four regions every five minutes is ~34,000 executions and ~$19/month for a site that costs pennies. The metric alert covers the same failure mode for a tenth of a dollar.

ADR-06 · Secrets out of the repo

Deployment token lives in GitHub Actions secrets; the storage key lives in Static Web App app settings. The repo is public and contains neither.

Why: a portfolio repo is meant to be read. Anything that must stay private stays out of it — and Bicep is written so no secret ever lands in deployment output.

Live API

Same-origin, no keys, no CORS preflight. These are real endpoints you can call right now:

GET/api/healthliveness, runtime, region, uptime, integration flags
GET/api/visitsincrements and returns the visit counter
POST/api/contactvalidates and stores a message (name, email, message)

Observability: every invocation emits requests and dependencies to Application Insights (30-day retention), and an Azure Monitor metric alert emails me if the edge 5xx ratio passes 5% over 15 minutes. The badge above is a real round-trip to /api/health, not a decorative label.

What this page is really showing

The claim "I know Azure" is cheap. A public repo with Bicep, a workflow that deploys on push, a serverless API with a real data store, telemetry wired in, and an availability signal on the page — that is the difference between describing experience and demonstrating it.

Everything is small on purpose: the point is that every layer is visible and none of it is decorative.
