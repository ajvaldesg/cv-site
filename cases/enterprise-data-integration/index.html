Case 01 · Data platform

Hybrid data integration inside a regulated utility

Integrating vendor, on-premises and Azure data in an environment where the network is not open, the change process is slow by design, and every environment must look exactly like production before code is allowed near it.

Context and constraints

The data lived in three places that could not be merged and could not be moved at will: vendor systems outside the organisation's control, on-premises systems inside the operational network, and an Azure estate that had to remain the governed target. In a regulated utility, the constraint list comes before the technology list:

inbound network access does not get opened for convenience; secrets do not live in code or configuration files; production is not available for experiments; and the evidence trail for change is part of the deliverable. Any design that ignored those four points would have been technically valid and organisationally undeliverable.

The private network never accepts inbound connections from Azure: the self-hosted Integration Runtime reaches outward, so connectivity exists without opening the operational perimeter. Everything inside the Azure boundary is reached through RBAC, with secrets brokered by Key Vault rather than stored in pipelines.

Decisions and trade-offs

Self-hosted Integration Runtime instead of network exposure

On-premises sources are reached through a runtime that lives inside the private network and initiates outbound connections. The perimeter stays closed and the security team does not have to approve a new inbound path for every source added later.

Accepted cost: a component to host, patch and monitor on the customer side, and a dependency on that host's availability for every pipeline that touches it.

SecurityConnectivityOperability

Metadata-driven orchestration over bespoke pipelines

Azure Data Factory is used as the control plane: sources, targets and schedules are described rather than hand-coded per integration, so onboarding a new vendor feed is a configuration exercise instead of a new project.

Accepted cost: more design effort up front and a framework that must be maintained — worth it the moment the second and third source arrive.

ScalabilityMaintainability

Event-driven processing in Functions, batch movement in Data Factory

Movement and transformation are separated by trigger type: scheduled batch in Data Factory, reactive handling in Azure Functions. Each workload gets the execution model that fits it instead of forcing everything through one tool.

Accepted cost: two runtimes to observe, and the need for clear ownership of what happens where when a pipeline fails mid-flight.

ReliabilitySeparation of concerns

Four isolated environments, including a separate UAT

DEV, QA, UAT and PROD are separated so that vendor integration and business sign-off happen against an environment that reflects production, not against a developer's approximation of it.

Accepted cost: four times the configuration surface and a promotion path that must be disciplined, or drift appears between environments and the UAT signal becomes worthless.

GovernanceRiskRegulated change

Secrets in Key Vault, authorisation through RBAC

Connection details are resolved at runtime from Key Vault, and access to data and orchestration is granted by role rather than by embedded credentials. Rotation stops being a code change.

Accepted cost: identity and access work moves earlier in the delivery cycle, and every role assignment becomes something to review.

Governance, security and scale

Security was structural, not additive. NSGs define what can talk to what, RBAC defines who can do what, and Key Vault holds what must never be written down. None of those three is a step at the end of the pipeline.

Governance followed the environment model. With DEV, QA, UAT and PROD separated, promotion is an explicit, reviewable act, and test evidence is produced against an environment that looks like the one that will run in production.

Scale shaped the design, not the other way round. More than two terabytes a day means the architecture has to assume partial failure as normal: a run that dies halfway must be restartable, staging must be durable, and monitoring has to answer "which source, which window, which environment" without a person reconstructing it from logs.

Ownership covered the whole delivery path. Design, build and test planning were owned together — which is what keeps an integration architecture honest, because the test strategy exposes the decisions that looked elegant on a diagram.

What this case demonstrates

Designing under constraint: connectivity you cannot open, environments you must replicate, secrets you cannot store, and a volume that makes failure handling a first-class concern. The result is an integration platform that the security and operations functions can accept — which is the only definition of "done" that survives contact with a regulated business.

Scope note: the figures shown (2 TB+ daily, four environments, ownership of design, build and test planning) are the ones recorded for this engagement. No cost, team-size or timeline figures are asserted here.
